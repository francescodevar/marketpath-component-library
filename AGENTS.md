# AGENTS.md

Static component gallery (Astro, `output: "static"`) for Marketpath CMS: Bootstrap 5.3 wireframes with Marketpath Liquid templates and Custom Fields JSON. **No backend.** `astro build` pre-renders a single HTML page to `dist/`; Bootstrap, Bootstrap Icons and Prism load from CDN at runtime.

## Purpose and design priorities

- This is a reusable **Marketpath CMS component library**, not a website builder or a set of one-off pages. Each catalog component should be portable and easy to copy into an existing Marketpath project with its Liquid template, Fields, preview, sample data, and implementation notes.
- Build once, reuse across projects. Preserve a component's field/data contract across visual variants; share identical Page Fields from `<category>/shared-fields.js` and shared datastore schemas rather than duplicating or renaming fields.
- Prefer real Bootstrap 5.3 components and example patterns as the starting point: [official Bootstrap snippets](https://getbootstrap.com/docs/5.3/examples/#snippets). Use the project's existing CDN/framework and conventions; add custom CSS, dependencies, or extra files only when the required behavior cannot reasonably be expressed with them.
- Before adding a component, verify it remains self-contained, copyable, discoverable, and compatible with the catalog's Fields/Datastore panels and static preview.

## Commands

- Install: `bun install`. Dev: `bun run dev` (`http://localhost:4321`). Build: `bun run build` → `dist/`. Preview: `bun run preview`. Needs Internet for CDNs.
- Verify: `node tests/check.cjs` (or `bun run check`; plain Node, no Astro build needed). **Run this after every edit/addition under `src/catalog/`.**

## Layout

- `src/catalog/<category>/<id>/component.js` — one template per folder, exporting its definition as `export default { ... }` (metadata, template, page `fields`, optional datastore references, preview, mockData, notes). Use `datastoreId` for one schema, `datastoreIds` for multiple schemas, and `entityDatastoreId` when the current `entity` is backed by a datastore item.
- `src/catalog/<category>/shared-fields.js` — reusable Page Custom Fields for variants that share FieldIDs; import the same field definitions and set a matching `sharedFieldsId` on each variant. If only part of the Fields is shared, list those IDs in `sharedFieldIds`; keep variant-specific fields distinct.
- `src/data/components.js` — auto-discovers `src/catalog/**/component.js` with Vite `import.meta.glob`; do not maintain a manual component list.
- `src/datastores/<id>/datastore.js` — shared Marketpath datastore schema; `src/data/datastores.js` auto-discovers these. Multiple components reference one schema by `datastoreId`.
- `src/components/ui/ComponentCard.astro` — shared gallery card UI; keep the card shell/design here, not duplicated in template folders.
- `src/pages/index.astro` — gallery page, pre-rendered from the catalog; categories, filters, counts, and cards derive from discovered modules. Thumbnails use `previewDocument(component, { bootstrap: false })`.
- Category navigation groups discovered categories into Services, Projects, Layout, Resources, and Content using `categoryGroups` in `src/lib/utils.js`; keep the main catalog and Playground filters in sync with those groups. Services contains Services and Inside Services; Projects contains Projects and Inside Projects. Only one main-catalog dropdown group should stay open at a time.
- `src/scripts/gallery.js` — client search/filter/dialog/tabs/copy/preview. `src/lib/utils.js` — shared `escapeHtml`/`categoryLabel`/`previewDocument`.
- `src/layouts/Layout.astro`, `src/styles/app.css` — shell and styles. `tests/check.cjs` asserts the catalog invariants.

## Catalog contract (enforced by `tests/check.cjs`)

Each `component.js` default-export object must satisfy:

- Normally `prefix` === `id.replaceAll('-', '_') + '_'`. When variants share all copyable Page Fields, define them once in `<category>/shared-fields.js`, import the same array, set `sharedFieldsId` to the category, and use `${category}_` as the prefix (e.g. Services and Gallery); their Field arrays must be identical. When variants share only a common subset, import those definitions, list their IDs in `sharedFieldIds`, and keep variant-specific FieldIDs distinct. IDs are unique except when components intentionally import the exact same schema. Repeatable `fieldset` child IDs are local to each `item` (`icon`, `title`, `description`) and are validated in that loop scope.
- `preview.html` is hand-written static HTML: no `{{` or `{%`, and all its `data-bs-target="#..."` IDs must exist. It is **not** rendered from the template or `mockData`.
- When extending a component with existing CMS Fields, preserve its established FieldIDs and prefix; use a stable `sharedFieldsId` matching that legacy prefix rather than renaming fields already in use.
- `template`: every field is referenced as `entity.<FieldID>`; every output sits inside an `if entity.<field>.is_valid` guard; `url` fields use `.value | escape`. Liquid `if`/`endif` must balance.
- Field `Type` limited to `text`, `textarea`, `url`, `image`, `imagelist`, `taglist`, `toggle`, `html` (`html` is used by `content-02`, all Services components, the image Gallery, and CTA datastore content; its output renders raw), plus `select` and `radio` (both require `Options` + `Delimiter`; radio fields do not support `Validators`), `datastoreitem` and `datastoreitemlist` (require `DatastoreGUID`; single-item CTA references are shared by CTA variants; the list types are used by Services and testimonials), and repeatable `fieldset` (`AllowMultiple: true`, used by `banner-03`). `image`/`toggle` must have no `Validators`. Group nodes have no `FieldID` and a non-empty `Fields`.
- `toggle` fields use the full switch shape: `OnLabel`/`OnValue`/`OnColor` + `OffLabel`/`OffValue`/`OffColor` + `DefaultValue` (e.g. `OnValue: "On"`, `OnColor: "success"`, `OffValue: "Off"`, `OffColor: "secondary"`).
- Use **generic sample content** everywhere (`preview.html`, `mockData`, notes, placeholders): never a real client's name or copy. The sample brand is `Example`; sample people are `John Doe`/`Jane Smith`.
- Sections use `py-5` with `container py-2` — no stacked spacing combos (`mt-2 py-lg-2`-style) unless the component is a banner. The solid Page Title 01 is deliberately `py-4`; the image Page Title 02 is `py-5`. If a template/preview references non-Bootstrap CSS (e.g. removed `text-intro-section`, `highlights`, `highlight-icon`), flag it and remove it.
- Prefer Bootstrap 5.3 components and utilities for layout, spacing, colors, typography, and buttons (`btn btn-primary`, `text-primary`, `bg-primary`), following the official snippets linked above. Add custom CSS only when Bootstrap cannot reasonably express the required behavior, and keep `customCss` metadata accurate.
- `customCss` must be true when a template contains `style=`, uses the Marketpath `img ... style:` argument, or uses `add_stylesheet inline`; otherwise false. `customJs` must reflect Marketpath `add_javascript` usage. Templates must not contain literal `<script`, `<style`, `{{#if`, `py-lg-8`, or `entity.is_valid`.
- `faq-01`, `faq-02`, `gallery-01`, and `gallery-02` set `bootstrapJs: true` (need the Bootstrap bundle); others are `false`. `testimonials-01`, `banner-04`, `gallery-01`, `gallery-02`, and `gallery-03` use custom JavaScript.

## `settings` object (not in this catalog's tests)

Marketpath templates expose a global `settings` object alongside `entity`; read fields as `settings.<FieldID>`, with `.value` for stored values — e.g. `settings.logo_image.value`, `settings.company_email`, `settings.header_cta_link.value`. Built-in entity properties such as `entity.title`, `entity.browser_title`, `entity.object_type`, `entity.url`, and `entity.full_url` are not Page Custom Fields.

Settings schemas use further field types such as `menu` and `menuitemlist`; `select` and repeatable `fieldset` are also supported by catalog components. Extra properties seen in settings fields: `DefaultValue`, `Collapsed`/`InitCollapsed`, `RequiredMessage`, `DoNotValidateCustom`, and `Validators` such as `{"Type": "email"}`. The `tests/check.cjs` allowlist applies to objects under `src/catalog/`; settings/header/footer schemas may use further types.

`settings` is loaded from the shared **Page Settings** datastore in the MPSS1 header. Header variants and all footer variants read its global fields; `banner-02` also reads `company_address`/`company_email`. The catalog tests ignore `settings.*` references. `footer-01`, `footer-02` and `footer-03` have no page Custom Fields, declare `settingsDatastoreId: 'page-settings'`, and use a shared Light/Dark preview theme picker.

## Gotchas

- **Playground edits reach the import.** Text edited in the theme builder preview is linked to data (`src/scripts/playground.js`, `buildBlockBindings`): a component's `mockData` strings are matched to the smallest preview element with the same text, and a `mockData` list that stands for a datastore field (service cards…) is bound by position. Edits are stored as `block.values` (a copy of `mockData`, used by `pageFieldsForInstances` instead of `mockData`) and `themeWorkspace.datastoreEdits` (`{ services: { 0: { Title } } }`, merged over `exampleDatastoreItems` by `mergeDatastoreEdits`; unknown keys and `Name` are ignored). So keep `mockData` texts in sync with `preview.html`: a field whose text is not in the preview shows as disabled. `node tests/theme-edits.mjs` covers the export side.

- Gallery 01 filters use `tag:{{ tag.name.value | url_encode | escape }}` consistently for buttons, mobile options, and image tags. The prefix avoids colliding with the special `all` filter; URL encoding protects comma-delimited names. Do not pipe `tag.guid` into `escape`: Marketpath returns a System.Guid conversion error, making every filter share the same error string. Labels use `tag.title.value` with a `tag.name.value` fallback. Its sample data uses `filters` to fill `gallery_filters`. Export sample tags with both `Name` and `Title`, and include referenced ImagePresets in component packages. The gallery lightbox is moved to `document.body`; keep its `gallery-component gallery-lightbox` classes so styles survive reparenting. Its modal/backdrop levels are 10001/10000 to cover Header 02's z-index 9999 without changing the header.

- Every header, including Playground theme exports, must preserve `{%- add_stylesheet "/main.scss" -%}` and `{%- add_javascript "/bootstrap5/js/bootstrap.bundle.min.js" defer:true async:true position:'body' -%}`. Do not strip these tags during export or add a second Bootstrap JavaScript bundle from a CDN.

- Main Services component imports must contain only the selected component partial and its example page template. Even with page examples enabled, never append service-detail templates, individual service routes, or a Services datastore default detail template. Inside Services detail templates and their FAQ dependencies belong only to explicit Inside Services component imports.

- Marketpath component import format: see `docs/marketpath-imports.md`, based on the user-provided `services-page-example.zip`. An Article page requires its own `Article` record and `TemplateGUID`; match the reference URL shape `//target-domain/path`. `Datastore.DefaultRootPath` does not replace `Article.URL`. Example content defaults to datastore items and images without Articles or routes and needs no target domain. A separate, initially unchecked page-example option requests the target domain and Article route. Register binary images in `Image` with a matching `FileGUID`. Keep FAQ examples scoped to components declaring the FAQs datastore. Do not copy Article metadata over DatastoreItem identity when filling entity Page Fields.

- `tests/check.cjs` discovers component folders recursively and derives the component count and field total; it also protects shared schemas and important per-component contracts, including FAQ-01's three static preview items. Adding a template means creating one folder/file; no central component list, homepage, or component-count edits.
- Preview thumbnails always render with `bootstrapJs:false` (`src/components/ui/ComponentCard.astro`, via `previewDocument(..., { bootstrap: false })`); only the detail iframe loads the Bootstrap bundle, so FAQ and Gallery lightboxes are not interactive in thumbnails. Preview iframes are `sandbox`ed with a strict CSP (`src/lib/utils.js`) that only allows the Bootstrap/Bootstrap Icons CDN (`font-src https://cdn.jsdelivr.net`) plus an injected `.text-small` helper. Banner 02 and Banner 03 previews/templates use Bootstrap Icons; the icon stylesheet is load-bearing for them. Banner 04 uses Marketpath Swiper CSS/JS in its template; its hand-written preview is a static logo row.
- Liquid here is Marketpath-specific, not Shopify: `entity` root, `.is_valid`, `.value` for URL, `img ... preset:` tag.
- Components with a `datastoreitem` or `datastoreitemlist` declare their referenced schema(s) via `datastoreId` or `datastoreIds`; `entityDatastoreId` identifies datastore fields read directly from the root `entity`. The global **View Datastore** button beside the results summary shows/copies shared datastore item fields. The Fields panel remains for page Custom Fields only. CTA 01/02 share the `cta_datastore_item` Page Field and the `call-to-action` datastore. Services 01/02/03 import identical Page Fields from `src/catalog/services/shared-fields.js` (`services_eyebrow`, `services_title`, `services_description`, `services_items`) and share the Services datastore fields `services_image`, `services_summary`, and `services_content`; all service card titles come from the datastore item’s default `title`. Services 02 Stack Cards use `services_summary` as the card excerpt; full `services_content` belongs on Generic Pages / Inside Services.
- Projects 01 reads the shared Projects datastore (`project_image`, `project_summary`, `project_content`, `project_images`, `projects_details`, `project_overview`) through `projects_items`; card link/title are the datastore item `full_url`/default `title`. The full card is one anchor. Project cards show image/title/action; detail content belongs in a separate project detail template.
- Testimonial variants share `src/catalog/testimonials/shared-fields.js` (`testimonials_section_title`, `testimonials_intro_text`, `testimonials_section_items`) and the `testimonials` datastore. Each item uses its default `title` as the reviewer name, `testimonial_text` as rich HTML, and optional `testimonial_highlight` as a short label. Keep Page Fields, shared IDs, and datastore GUID placeholders aligned across variants.
- Uncomment/duplicate variants require renaming both `FieldID` references and HTML element IDs (e.g. accordion) to avoid collisions. FAQ-01 and FAQ Main (FAQ-02) share the FAQs datastore and common title/description/list Fields; the Main layout adds an optional eyebrow. `footer-01`, `footer-02` and `footer-03` use global Page Settings; `services-01`, `services-02`, and `services-03` use a variable-length `datastoreitemlist` and need their `DatastoreGUID` placeholders replaced.
- Generic Pages / Inside Services reads the current service record from the Services datastore and references Services and FAQs from Page Custom Fields. Generic Pages / Inside Projects reads the current project record from the Projects datastore. Use `datastoreIds` for the schemas and `entityDatastoreId` for the root item.
- Required CMS image presets referenced by templates: `1920x1080-crop`, `800x600-crop`, `1920x600-crop`, `720x480-crop`, `1200x675-crop webp` (Inside Services), `700x394-crop webp` (Inside Projects), `800x450-crop webp` (Projects Cards), `300x300-max` (Banner 04 logos), `960x540-crop`, `600x338-crop`, and `200x200-crop` (Blog 01). They are project requirements, not built-ins.
- Bootstrap 5.3 is standard; `py-lg-8` is deliberately omitted. Negative-margin utilities (`mt-n*`) are **disabled in the stock CDN build** (`$enable-negative-margins`), so don't use them for overlap. Hero 01, Banner 02, Services 02, Testimonials 01, Banner 04, Header 01, Header 02, and Blog 01 set `customCss: true` for inline styles or component-specific CSS.
- `README.md` is in Spanish; treat it as prose reference, not executable truth when it conflicts with `tests/check.cjs`.
